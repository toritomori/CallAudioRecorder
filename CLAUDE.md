# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## О проекте

WPF-приложение (net10.0-windows) для записи звонков: микширует системный звук (WASAPI loopback) и микрофон в MP3, ведёт живую транскрипцию на русском или английском (sherpa-onnx + GigaAM v3 / Parakeet TDT + Silero VAD) и формирует итоги встречи через локальный Ollama. Весь UI, комментарии и строки — на русском языке; придерживайся этого стиля (кроме англоязычных промптов и меток спикеров для английского режима).

## Команды

```powershell
dotnet build   # решение целиком: sln и csproj одноимённые, поэтому MSBuild сам берёт .sln
dotnet test    # юнит-тесты, без моделей и Ollama
dotnet run
```

**Юнит-тесты** (`CallAudioRecorder.Tests/`, xUnit) закрепляют чистую логику с порогами, подобранными по корпусу: правила `TermCanonizer`, `VersionNormalizer`, голосование `SpeakerNamer`, `WithoutFillers`/`SplitByBudget`, порядок ленты `AppendRecognized`, разбор ответа `TranscriptCorrector`, параметры запроса `OllamaClient.ChatOptions` (потолок ответа `num_predict`, окно только для локальных моделей). Модель подменяет `FakeChatClient` (реализует `IChatClient`): заготовленные ответы, обрыв по окну (`DoneReason = "length"`), облачный бюджет (`int.MaxValue`). Меняешь правило или порог — сначала `dotnet test`, затем корпусный CLI-прогон.

- Тестовый проект лежит в подпапке, основной `.csproj` исключает её через `DefaultItemExcludes` — иначе SDK компилирует тесты в приложение. `internal` открыты тестам через `InternalsVisibleTo`.
- `dotnet build -o <папка>` — только с `CallAudioRecorder.csproj` (для решения `-o` не поддерживается); во временную папку собирай, когда запущенное приложение держит `bin`.

**Интеграционное** — аудио, модели распознавания, живой Ollama, вёрстка, корпус — осталось в скрытых CLI-режимах (приложение — WinExe, консоли нет, результат пишется в лог-файл; первая строка лога — `OK` или `FAIL`):

```powershell
# Запись N секунд без окна (проверка аудиотракта)
CallAudioRecorder.exe --selftest <лог-файл> [секунды]

# Замер скорости распознавания (RTF) на WAV-файле; язык — ru (по умолчанию) или en (только Debug)
CallAudioRecorder.exe --stt-test <лог-файл> <wav-файл> [ru|en]

# Самотест диаризации: два WAV с разными голосами → «Собеседник 1»/«Собеседник 2» (только Debug)
CallAudioRecorder.exe --diar-test <лог-файл> <wav1> <wav2>

# Сквозной тест: запись + живая транскрипция N секунд
CallAudioRecorder.exe --stt-selftest <лог-файл> [секунды] [ru|en]

# Итоги встречи по тестовому транскрипту через Ollama
CallAudioRecorder.exe --summary-test <лог-файл> <модель>

# LLM-коррекция транскрипта с искажёнными терминами
CallAudioRecorder.exe --fix-test <лог-файл> <модель> [ru|en]

# LLM-коррекция готового транскрипта целиком (без шага имён): партии и время каждой
CallAudioRecorder.exe --fix-file <лог-файл> <файл .транскрипт.md> <модель> [ru|en]

# Итоги по синтетическому транскрипту длинной встречи (проверка окна контекста)
CallAudioRecorder.exe --summary-long-test <лог-файл> <модель> [минуты] [ru|en]

# Диаризация готовой записи: спикеров до и после консолидации, близость центроидов
# (последние два аргумента — пороги слияния, для калибровки; только Debug)
CallAudioRecorder.exe --diar-file <лог-файл> <mp3 или wav> [порог] [порог-для-осколков]

# Имена участников по сохранённому транскрипту: какая метка чьим именем становится
CallAudioRecorder.exe --names-test <лог-файл> <файл .транскрипт.md> <модель> [ru|en]

# Канонизация терминов по глоссарию и номеров версий на готовых транскриптах:
# все замены с частотой
CallAudioRecorder.exe --canon-test <лог-файл> <файл .транскрипт.md или папка>

# Снимок окна в PNG + проверка вёрстки на наложения блоков (окно не показывается на экране)
CallAudioRecorder.exe --ui-shot <png-файл> <лог-файл>

# Захват звука отдельного приложения; PID=0 — список окон-кандидатов
# Режимы: all (по умолчанию), direct (только ProcessLoopbackCapture), engine (только RecordingEngine)
CallAudioRecorder.exe --proc-loopback-test <лог-файл> [PID] [секунды] [режим]
```

Режимы объявлены таблицей «флаг → обработчик» в `Diagnostics/DiagnosticModes.cs`; сами режимы — в `Diagnostics/` по темам (`AudioChecks`, `SttChecks`, `LlmChecks`, `TextChecks`, `UiShot`). Пробники `--stt-test`, `--diar-test`, `--diar-file` (`SttSpike.cs`, `DiarSpike.cs`) закрыты `#if DEBUG` — в Release-сборке их нет. Новый режим — строка в таблице и метод в файле своей темы; `App.xaml.cs` не трогать. STT-режимы требуют скачанных моделей, `--summary-test`/`--fix-test`/`--summary-long-test` — запущенного Ollama на `localhost:11434`. `--summary-long-test` считает успехом только ответ со всеми пятью разделами итогов и `done_reason=stop`.

- `.ps1` с кириллицей сохраняй в UTF-8 с BOM: PowerShell 5.1 читает файл без BOM как ANSI, и путь к `Запись_*.транскрипт.md` не находится.
- «Исправить текст» перезаписывает `.транскрипт.md` уже с именами вместо меток — `--names-test` на таком файле не повторит исходный замер; для калибровки `SpeakerNamer` нужен транскрипт до исправления.

## Архитектура

Конвейер: **RecordingEngine** (аудио → MP3 + tap-потоки; системный канал — либо WASAPI loopback устройства, либо **ProcessLoopbackCapture** выбранного приложения) → **TranscriptionService** (tap'ы → реплики, термины по пути канонизируются **TermCanonizer**) → **OllamaClient** + **SummaryComposer**/**SummaryPrompt** / **TranscriptCorrector** (транскрипт → итоги / исправленный текст). `MainWindow.xaml.cs` связывает всё это с UI (MVVM не используется — code-behind).

### RecordingEngine.cs — запись

Системный канал (`IWaveIn`: loopback устройства или звук одного приложения) + микрофон → `BufferedWaveProvider` → ресемпл в 48 kHz stereo → `MixingSampleProvider` → LAME MP3. Ключевой инвариант: поток записи вытягивает из микшера ровно столько кадров, сколько прошло по `Stopwatch` (clock-driven pull), а `ReadFully = true` заполняет пустые буферы тишиной — поэтому паузы системного звука не «съедаются» и потоки не разъезжаются. При `enableTranscriptionTaps` дополнительно отдаёт `MicTap16k`/`SystemTap16k` (16 kHz mono float) для распознавания.

### Services/TranscriptionService.cs — живая транскрипция

Два «насоса» (по потоку на канал) читают tap'ы со скоростью реального времени — благодаря нулям тишины индекс сэмпла = время записи. Каждый насос кормит свой Silero VAD; сегменты расширяются на 0.3 с в обе стороны через кольцевой буфер `AudioRing` (VAD режет впритык) и складываются в общую очередь, которую разбирает **один** `OfflineRecognizer` (чтобы не выедать CPU у MP3-пути). Спикеры жёстко именуются: микрофон = «Я», система = «Собеседник» или «Собеседник N» при диаризации (`TranscriptEntry.IsMe` завязан на строку «Я»).

Hotwords работают только с transducer + `modified_beam_search` и только в алфавите модели: словарь GigaAM почти не содержит латиницы (85 токенов из 1025), английский Parakeet — кириллицы. Поэтому в русском режиме английские термины неизбежно искажаются («эйпиай», «дед лайн»); их восстанавливает LLM-коррекция (`TranscriptCorrector`), а не параметры распознавателя — не пытайся чинить это на стороне ASR. Смешанная ru/en речь в одной записи не поддерживается: модель одна на запись.

**После записи профили пересобираются** (`SpeakerDiarizer.Consolidate`, вызывается из `StopAndDrain`): живое решение принимается по первому же сегменту и назад не смотрит, поэтому плодит фантомов — на корпусе из 30 записей 39 % профилей набрали не больше двух реплик, а «собеседников» выходило 8.6 на встречу при примерно пяти реальных. Консолидация сливает профили по близости центроидов, посчитанных уже по всем сегментам, и перенумеровывает оставшихся по порядку появления. Замерено `--diar-file` на часовой записи: 14 профилей → 9, все осколки на 1–2 репликах исчезли.

Пороги (`MergeThreshold` 0.60, `WeakMergeThreshold` 0.48 для профилей короче трёх надёжных сегментов) взяты из фактических расстояний: разные крупные спикеры дают 0.40–0.46, а осколок со «своим» спикером — 0.50–0.64. Диапазон узкий, поэтому 0.50 сливает 14 профилей в 3, а 0.65 не сливает ничего — меняешь порог, прогоняй `--diar-file`, он печатает попарную близость. Там же ловушка алгоритма: перебор пар нельзя обрывать на глобальном максимуме, у каждой пары свой порог.

**Лента в UI не равна порядку распознавания.** Каждый канал ждёт своего VAD, поэтому длинная фраза собеседника (00:29:38–00:29:50) попадает в очередь позже короткой реплики с микрофона в 00:29:48 — и «добавить в конец» показывало ответ выше вопроса, хотя в файле порядок был верным (`StopAndDrain` сортирует по времени). `AppendRecognized` кладёт реплику на своё место в плоский список и пересобирает блоки заново: доклеить на месте нельзя, потому что опоздавшая реплика не только встаёт в середину, но и РАЗБИВАЕТ блок, который до неё выглядел непрерывным. `MainWindow` затем обновляет только разошедшиеся элементы коллекции — перезаполнение целиком сбрасывало бы прокрутку. Проверяется `LiveFeedOrderTests` (бывший `--order-test`): 200 случайных перестановок, лента обязана совпасть с `MergeAdjacent` по отсортированным репликам.

Диаризация (`Services/SpeakerDiarizer.cs`, опциональна): реплики системного канала помечаются «Собеседник 1», «Собеседник 2», … (или «Speaker N» — метки берутся из `LanguageProfile`) — embedding голоса (CAM++ zh+en) на каждый распознанный сегмент, сопоставление с профилями по косинусной близости (порог 0.6; один голос ≈ 0.8+, разные ≈ 0.5 — калибровано по `--diar-test`). Сегменты короче 2 с не создают нового спикера и не уточняют центроид — только прилипают к ближайшему профилю (шумный embedding). Вызывается только из потока SttWorker (не потокобезопасен); нет модели на диске или ошибка — диаризация молча выключается, остаётся общий «Собеседник». Включается чекбоксом «Различать собеседников по голосу» (по умолчанию вкл, поле `diarizeSpeakers` в settings.json). Внимание: цвета имён спикеров в пузырях — это DataTrigger'ы в `MainWindow.xaml` по ТОЧНЫМ строкам «Собеседник 1»…«Собеседник 4»; при переименовании меток в `SpeakerDiarizer` нужно править и XAML.

### Services/TermCanonizer.cs — канонизация терминов

Приводит искажённые названия к написанию из глоссария **без LLM**, прямо в потоке распознавания
(`TranscriptionService` вызывает его перед созданием реплики; исходный текст остаётся в
`TranscriptEntry.RawText`, если что-то поменялось). Сопоставление идёт по звучанию: кириллица
транслитерируется в латиницу, диграфы и созвучные буквы сводятся к одной, дальше сравниваются
скелет согласных (быстрый фильтр) и полная звуковая форма (решающая проверка).

Пороги подбирались по корпусу из 45 транскриптов, и каждое правило появилось из конкретного
ложного срабатывания — не ослабляй их, не прогнав `--canon-test`:

- **Решает звуковая форма с гласными, а не скелет.** По одному скелету «задачки» неотличимы
  от «SDK», «были» от «build», «Артём» от «RTD»: на первом прогоне таких замен было 4081 из 4081.
- **Кириллическое слово заменяется только на термин с заглавной буквы.** Имя собственное
  в русском тексте не склоняется, а нарицательное заимствование склоняется: «в конфигах» после
  замены на «config» разваливается. Регистр в глоссарии — это и есть переключатель: `Poki`
  правит «поки», а `config` кириллицу не трогает.
- **Начало слова должно совпадать** (расстояние по первым двум звукам ≤ 1) — иначе «наполовину»
  и «плагин» притягиваются к AppLovin.
- **Слово с цифрами не канонизируется**, если в каноне цифр нет: «MVP6» — это MVP шестой.
- **Пара слов берётся, только если оба значимы** и разделены пробелом или дефисом. Иначе
  «BattlePass, да» схлопывалось в «Battle Pass» вместе с соседним словом.
- Термины со скелетом короче трёх согласных (`Poki`, `DM`, `UW`) сравниваются только целиком,
  по звучанию: иначе «Дима» уезжает в «DM», а «пока» — в «Poki».

Итог на корпусе: 261 замена на 5820 репликах, из них ложных — единицы (`--canon-test` печатает
все замены с частотой, глоссарий берёт из settings.json). Случаи из списка выше закреплены
в `TermCanonizerTests`: ослабь порог звуковой формы на единицу — упадут четыре теста.

### Services/VersionNormalizer.cs — номера версий

Распознавание съедает точки, и «1.8.3» приезжает как «183», «180» или «18.0» (в корпусе «183»
встретилось 47 раз, а правильное «1.8.3» — один). Отличить версию от обычного числа по одному
токену нельзя, поэтому нормализация идёт по записи целиком и вызывается из `StopAndDrain`,
а не в живом потоке: сперва собираются «семейства» версий встречи (канонически записанное
«1.8.3» или число рядом со словом «версия»/«билд»/«релиз»), затем к ним приводятся все числа
этих семейств. Правила против ложных срабатываний — «10 000» давало «0.0.0», а «сто процентов»
превращалось в «1.0.0»: первая цифра не может быть нулём, число не может быть частью большего
(«10 000»), а неподтверждённому семейству нужно либо второе соседство с маркером, либо пять
упоминаний. На корпусе: 74 замены, все — реальные 1.8.x/1.9.x.

Разрядность фиксирована: три цифры → `d.d.d`. Версии вида 2.10.0 так не соберутся.

### MainWindow.xaml — вёрстка левой колонки

**Инвариант: блок записи (таймер + кнопка + подсказка) живёт в отдельной строке Grid с `MinHeight`, а три карточки — внутри `ScrollViewer` (`SettingsScroll`) в строке `Height="*"`.** Раньше все четыре блока были строками `Auto`/`*` подряд, и каждый новый контрол в настройках отнимал высоту у кнопки записи: карточка «Выходной файл» наехала на таймер на 23 px, а подсказка — на строку состояния. Теперь при нехватке высоты прокручиваются карточки, а не уезжает главная кнопка.

Высота окна (920) подрезается по `SystemParameters.WorkArea.Height` в конструкторе — на крупном системном масштабе окно иначе не влезает в экран.

В шаблоне `DarkTabControl` (`App.xaml`) `ContentPresenter` обязан называться `PART_SelectedContentHost`: по этому имени `TabControl` отдаёт содержимое вкладки в UI Automation. Без него экранный диктор и UIA-скрипты не видели правую панель вовсе — ни ленты, ни кнопок «Исправить текст» и «Итоги». Содержимое невыбранной вкладки в дереве UIA не появляется, пока её не выберут.

Проверять глазами не нужно: `--ui-shot` рендерит окно в PNG (за пределами экрана, чужие окна не захватываются) и печатает геометрию блоков, пересечения и то, влезли ли карточки в зону прокрутки. Первая строка лога — `OK`/`FAIL`. После любой правки левой колонки прогоняй его.

### Services/LanguageProfile.cs — язык распознавания

Язык (русский/английский) выбирается в UI до старта записи и задаёт **всё языкозависимое разом**: модель распознавания, метки спикеров, фильтр глоссария, промпты LLM. Профиль (`LanguageProfile`) прокидывается в `TranscriptionService`, `SpeakerDiarizer`, `ModelDownloader`, `SummaryComposer`, `TranscriptCorrector`; новые языкозависимые вещи добавляй туда же, а не россыпью условий по коду.

- Русский — GigaAM v3 (~235 МБ), метки «Я»/«Собеседник N», hotwords только кириллицей.
- Английский — Parakeet TDT 0.6B v2 int8 (~660 МБ), метки «Me»/«Speaker N», hotwords только латиницей. Модель тоже transducer NeMo (`nemo_transducer`) и **держит `modified_beam_search`** — проверено, так что hotwords работают для обоих языков (RTF ≈ 0.11 против 0.14 у GigaAM).
- Модель второго языка не качается, пока его не выберут (`ModelDownloader.ModelsPresent(language)` / `MissingMegabytes`), — иначе первый запуск тянул бы ~900 МБ.
- Итоги и LLM-коррекция пишутся на языке записи: `SummaryPrompt.SystemFor/PartSystemFor/SectionsFor`, два системных промпта в `TranscriptCorrector`.
- `TranscriptEntry.IsMe` знает обе метки через `Languages.IsMeLabel`. Цвета имён в пузырях — по-прежнему DataTrigger'ы по ТОЧНЫМ строкам в `MainWindow.xaml`, теперь для «Собеседник 1»…«Собеседник 4» **и** «Speaker 1»…«Speaker 4»: меняешь метки в профиле — правь XAML.

### Services/ProcessLoopbackCapture.cs + AudioWindows.cs — звук одного приложения

Источником системного звука может быть не всё устройство вывода, а конкретное окно: `AudioWindows.Enumerate()` собирает видимые окна (EnumWindows, без cloaked и tool-window) и помечает «♪» те, чьи процессы сейчас играют звук; выбранный PID уходит в `ProcessLoopbackCapture` — `IWaveIn` поверх Windows Application Loopback (`ActivateAudioInterfaceAsync` на «VAD\Process_Loopback» с `AUDIOCLIENT_ACTIVATION_PARAMS`). Захват идёт по дереву процессов — иначе браузеры и Electron не записать: окно принадлежит главному процессу, а звук играет дочерний. По той же причине «играет звук» проверяется и по имени процесса, а не только по PID.

Три вещи, на которых легко обжечься (все проверены пробником на этой машине):
- **Документация Microsoft требует build 20348+, но на Windows 10 22H2 (19045) API работает.** Проверено: со звучащего процесса rms ≈ 0.07, с молчащего — ровные нули. Не выпиливай фичу по версии ОС; неподдерживаемая система сама вернёт ошибку активации.
- **Весь жизненный цикл COM-объектов — в одном MTA-потоке** (`Worker`): UI-поток WPF живёт в STA, а клиент должен создаваться, использоваться и освобождаться в одном апартменте.
- **Перед активацией обязателен `GC.Collect()` + `WaitForPendingFinalizers()`.** Движок держит предыдущую активацию, пока живы её COM-обёртки, и вторая запись подряд падает на `Initialize` с `E_UNEXPECTED`. Пауза не помогает — помогает именно сборка мусора; `ReleaseComObject` и явное освобождение CCW обработчика не спасают.

Формат фиксирован (48 kHz, 16 бит, stereo): у псевдоустройства нет своего микс-формата, клиент обязан назвать его сам. Выбор источника не сохраняется в settings.json — PID живёт только до перезапуска приложения.

### Services/* — LLM-слой

- `OllamaClient` — стриминговый чат с локальным Ollama; типизированные ошибки `OllamaUnavailableException` / `OllamaModelMissingException` показываются в статусе как есть. Сервисы ниже принимают не его, а `IChatClient` (`ChatAsync`, `ChatStreamAsync`, `GetInputBudgetAsync`) — чтобы тесты подставляли `FakeChatClient`. Резерв ответа (`responseTokens`) уходит в Ollama и как потолок генерации `num_predict` (`OllamaClient.ChatOptions`): без него зациклившаяся модель писала до конца окна — на `--names-test` записи от 20.08 это 144 с вместо 17, а скопированные ею фразы транскрипта давали кандидатов в имена «Вот» и «Там». `done_reason = "length"` теперь значит «упёрлась в окно или в потолок ответа».
- `SummaryComposer` — итоги с оглядкой на окно контекста; перед отправкой отсекает реплики-поддакивания (`WithoutFillers`: «угу», «ага», «э-э» — 5 % реплик корпуса, но всего 1 % символов, так что смысл в чистоте промпта, а не в экономии окна). «Да», «нет», «хорошо» и «понял» намеренно остаются: короткое «да» бывает ответом на вопрос, от которого зависит решение. короткая встреча идёт одним запросом, длинная — конспект каждой части, затем итоги по конспектам (прогресс через `IProgress<string>`). Конспект части ограничен `PartResponseTokens` = 4096 — это и потолок `num_predict`; если конспект всё же оборвался (`done_reason = "length"`), часть делится пополам и конспектируется заново, а оборванное сжатие группы конспектов оставляет её конспекты как были: иначе хвост части молча выпадал бы из итогов. Глоссарий идёт в промпт обоих проходов (`SummaryPrompt.BuildGlossaryBlock`) и учитывается в бюджете частей — он повторяется в каждой.
- `SummaryPrompt` — сами промпты итогов. **Формат ответа — только маркированные списки, без таблиц:** итоги копируют в Slack, а Markdown-таблицу он не отображает, и задачи приезжали туда строкой из палок и дефисов. Задача пишется одной строкой «что сделать — исполнитель: X — срок: Y»; формат задан примером, а не описанием — 9B-модель держит образец строки заметно устойчивее (по описанию она ставила «Задача: Исполнитель — срок» и перечисляла в исполнителях сразу всех участников, поэтому «исполнитель не назван» прописан явным вариантом). Пять разделов фиксированы (`SectionsFor`, по ним же `--summary-long-test` проверяет, что ответ не оборвался). Промпт первого прохода (`PartSystemFor`) требует размеченного списка с пометками «Тема / Решение / Задача / Вопрос / Факт»: полнота конспекта важнее краткости — что в него не попало, в итоги уже не вернётся.
- `SpeakerNamer` — меняет «Собеседник N» на имена, которые прозвучали в разговоре (шаг кнопки «Исправить текст»). **У модели спрашивается только СПИСОК имён встречи, а кто из них кто — считается детерминированно.** Просить у LLM саму привязку бессмысленно: она системно путает направление обращения — на планёрке имя называют СЛЕДУЮЩЕМУ говорящему («Дальше, Дима.», «…в пятницу был два. Ира.», «Передаю слово давай Людмиле»), а модель отдавала это имя тому, кто его произнёс, и вся разметка встречи уезжала на одного человека; qwen3.5:9b к тому же на такой вопрос вместо формата «метка = имя» выдаёт поток рассуждений, из которого не разобрать ничего (на записи от 14.09 — 0 имён). Теперь привязка идёт голосованием: имя, названное у края реплики, — голос за спикера СЛЕДУЮЩЕЙ реплики; «я Марина» — голос за самого говорящего. **Голос считается уверенным только при явной передаче слова:** имя отдельным предложением, имя с запятой в начале предложения или короткое предложение с маркером («передаю слово», «дальше», «давай», «можно»). Без такого голоса имя не назначается вовсе — иначе пара упоминаний в третьем лице делает метку чужим именем. Метка остаётся как есть и при ничьей у метки, и когда на одно имя одинаково претендуют двое: «Собеседник 3» в задачах честнее чужого имени. Кандидаты из ответа модели отсеиваются по самому транскрипту — имя должно встречаться в нём написанным как имя собственное (с заглавной не в начале предложения или отдельным предложением), сверка с точностью до падежа («Артёму» = «Артём»). Имя владельца берётся из настроек (`ownerName`) и исключается из кандидатов; если поле пустое — спрашивается у модели отдельным коротким вопросом, потому что строке «Я = …» в общем ответе доверять нельзя (на трёх встречах из трёх она называла владельцем чужого). Замерено `--names-test` на записи от 14.09: 8 имён из 9 меток, все верные, девятая метка честно осталась меткой — слово ей никто не передавал; на записи от 17.08 — 5 из 9, тоже все верные. **Проверки «написано как имя» мало, когда модель зацикливается:** на записи от 20.08 qwen3.5-text:9b вместо списка копировала фразы транскрипта, и «Вот», «Там», «Поке» (распознавание пишет их отдельным предложением — «Вот.») прошли в кандидаты, а «Вот» отобрало метку у Вячеслава. Поэтому ещё два правила: кандидат, чьи падежные формы (`IsForm`: основа + окончание из короткого списка, «пока» — форма «Поке», а «верно» — не форма «Веры») в транскрипте чаще написаны со строчной, чем как имя, — не имя; и имя в чужом алфавите — не имя (латиница в русском транскрипте — только канонизированные термины глоссария: Poki, Google). Отсеянные печатаются в разборе `--names-test` строкой «отсеяны:». На пяти транскриптах корпуса правила не задели ни одного настоящего имени: у qwen3.5:9b разметка совпала с прежней по всем 68 меткам, у qwen3.5-text:9b запись от 20.08 стала такой же, как у qwen3.5:9b.
- `TranscriptCorrector` — исправление транскрипта в формате `[номер] текст`; при не-формате в ответе LLM исходный транскрипт возвращается нетронутым. Гонит реплики партиями: ответ здесь равен входу, поэтому в окно должны влезть оба. **Партия вместе с ответом укладывается в минимальное окно (`OllamaClient.MinContext` = 8192), а не в «40 % доступного»:** окно задаёт KV-кэш, и на 8 ГБ видеопамяти qwen3.5:9b при окне 20480 теряла 3 слоя из 34 на CPU — генерация ~26 токенов/с вместо ~59. Коррекция почти вся — генерация, поэтому встреча на 526 реплик шла 12:50, а мелкими партиями — 5:48 (`--fix-file`; скорость и раскладка слоёв — в `server.log` Ollama). Закреплено `TranscriptCorrectorTests.LongTranscript_EveryBatchFitsMinimalWindow`. Там же `ToHotwords` — фильтрует глоссарий до кириллицы.

**Глоссарий — один список на четыре задачи:** hotwords распознавателя (`ToHotwords`, только алфавит модели), детерминированная канонизация терминов (`TermCanonizer`), подсказка при LLM-коррекции и подсказка при формировании итогов. Черновик, собранный по накопленным транскриптам, — `docs/глоссарий.md`; там же видно, зачем он нужен: чем реже звучит название, тем сильнее его разносит распознавание (interstitial — 16 написаний и ни одного верного, Firebase — 10 написаний при одном верном, тогда как частые Crazy Games и BattlePass верны в 85 и 75 % случаев). Без списка разнобой протекает в итоги: на реальной записи от 20.08 одна фамилия («Шустов»/«Шутов»/«Шестун») дала в списке задач двух разных ответственных. Замерено на `Запись_2026-08-14_11-11-55`: без глоссария модель придумывает «Appluvia Mediation», «Tutorel», «Poke», с глоссарием пишет Poki, Firebase, Interstitial, Battle Pass. Но подстановку он не гарантирует — `Plavin` та же модель свела к «Platin Max» вместо AppLovin, так что редкие термины надёжно чинятся только детерминированной канонизацией до LLM.

**Окно контекста — главная ловушка этого слоя.** Ollama делит `num_ctx` между промптом и генерацией, а промпт длиннее окна молча урезает вместе с системной инструкцией: час разговора — это ~40 000 токенов (замерено: 115 425 символов = 41 810 токенов, ~2.76 символа на токен), и при фиксированном окне ответ вырождался в несколько строк не по формату. Поэтому `num_ctx` считается по длине промпта (`OllamaClient.EstimateTokens`, потолок `LocalContextCap` = 64k — Ollama выделяет KV-кэш сразу на всё окно), а что не влезло — идёт по частям. Облачным моделям (`remote_host`/`remote_model` в `/api/tags`) `num_ctx` не отправляется вообще: их окно задаёт сервер, и локальное значение может его только урезать. Обрыв по окну виден в `ChatOutcome.HitContextLimit` (`done_reason = "length"`) и показывается в статусе.
- `ModelDownloader` — докачка моделей (~262 МБ: GigaAM с HuggingFace + зеркало, VAD и CAM++ с GitHub releases) в `%LOCALAPPDATA%\CallAudioRecorder\models` с валидацией по минимальному размеру. Тег релиза speaker-модели содержит реальную опечатку «recongition» — не «исправлять».

### Файлы результатов

Рядом с `Запись_*.mp3` сохраняются `*.транскрипт.md` и `*.итоги.md`. Настройки UI — в `%LOCALAPPDATA%\CallAudioRecorder\settings.json` (там же `glossary` и `ownerName`; самотесты `--canon-test` и `--names-test` читают их оттуда, чтобы работать с теми же данными, что и приложение).

## Особенности потоков

Фоновые потоки не бросают исключения наружу — складывают их в свойство `Error`, которое UI опрашивает по таймеру (80 мс). `TranscriptionService.EntryRecognized` вызывается на фоновом потоке — в UI обязательно через `Dispatcher`.

- **`ConfigureAwait(false)` — в каждом `await` внутри `Services/`, и нигде больше.** Без него продолжения стриминга итогов сотнями возвращались в UI-поток. В `MainWindow` наоборот: продолжения обязаны остаться в UI-потоке, иначе обращение к контролам полетит из фонового. Правило держит анализатор (CA2007 включён только для `Services/**` в `.editorconfig`), так что забытый `ConfigureAwait` не соберётся. `IProgress` из UI (`Progress<T>`) по-прежнему доставляет отчёты в UI-поток сам.
- Потоки записи и насосы VAD останавливаются через `CancellationTokenSource`, а не `volatile bool`. Токен захватывается до старта потока, поэтому `Dispose` источника не роняет поток, который ещё не успел его прочитать. `ProcessLoopbackCapture` держит свои флаги: там это состояние `IWaveIn` (старт/стоп) в COM-потоке, а не только сигнал остановки.
